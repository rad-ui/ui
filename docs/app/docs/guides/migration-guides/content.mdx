# Migration guides

There has been no breaking release since `@radui/ui` 1.0. Patch and minor versions are drop-in: bump the dependency, run your tests, read the [changelog](/docs/first-steps/changelog) for anything marked as a behaviour change.

## Upgrading

1. Read the [changelog](/docs/first-steps/changelog) entries between your version and the target. Each entry says what changed, who it affects and how to adopt it; each component page links to its own history.
2. Bump `@radui/ui` and run the type check. Renamed or narrowed props show up as TypeScript errors.
3. Smoke-test the surfaces that depend on DOM structure: overlays (Dialog, Popover, Select), forms, and any CSS that targets Rad UI's generated classes or `data-*` attributes.
4. If you import `@radui/ui/themes/default.css`, keep `Theme classNamespace="rad-ui"` so the stylesheet's selectors still match.

## When a major version ships

A major release gets a guide on this page with the breaking changes, a before/after example for each, and the recommended updates that are not breaking. The release's changeset carries a `BREAKING` note ([Changeset quality](/docs/contributing/changeset-quality)), and codemods, when they exist, are listed under [Upgrade and codemods](/docs/contributing/upgrade-and-codemods).

## Coming from another library

Part names and composition will look familiar if you have used Radix UI: `Root`, `Trigger`, `Portal`, `Content`, `asChild`. The differences that matter during a port:

- Imports are per component: `import Dialog from "@radui/ui/Dialog"`, then `Dialog.Root`.
- State lives on `data-*` attributes, both as `data-state="open"` and as a boolean `data-open`, so either selector style works ([Styling and customization](/docs/guides/styling-and-customization#state-attributes)).
- Form controls render their own hidden inputs and submit, validate and reset with a native form ([Form submission](/docs/guides/hidden-input-strategies)).
- The theme is optional. Nothing renders styled until you import Clarity and set `classNamespace`.
