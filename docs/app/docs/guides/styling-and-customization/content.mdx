# Styling and customization policy

How Rad UI expects consumers to customize appearance without coupling to internal implementation details.

## Headless by default

Rad UI owns **behavior**, **accessibility**, and **composition**. Visual design is yours unless you opt into Rad UI's default theme CSS and `Theme classNamespace` classes.

Without `classNamespace` and without importing theme CSS, components render **without library-owned styling classes**.

## Supported customization surfaces

Use these stable hooks when styling:

| Surface | Example | Intended use |
| --- | --- | --- |
| `className` on parts | `<Button className="billing-cta" />` | local layout and app-specific styles |
| `data-*` state attributes | `[data-state="open"]`, `[data-open]` | state-driven styling in your CSS |
| `Theme` props | `appearance`, `accentColor`, `radius`, `scaling` | subtree-wide visual context |
| `Theme classNamespace` | `classNamespace="rad-ui"` | generated part classes that match theme CSS |
| `customRootClass` | per-component namespace override | incremental migrations |
| documented CSS variables | `--rad-ui-radius-md` | tokenized styling when theme CSS is loaded |

See [Usage](/docs/first-steps/usage) for `Theme` and `classNamespace` examples.

## State attributes

Every element with a `data-state` also carries a boolean attribute for it, so you can use a plain attribute selector or a Tailwind `data-*` variant:

| `data-state` | Boolean attribute |
| --- | --- |
| `open` / `closed` | `data-open` / `data-closed` |
| `checked` / `unchecked` / `indeterminate` | `data-checked` / `data-unchecked` / `data-indeterminate` |
| `on` (toggles) | `data-pressed` |
| `complete` (progress) | `data-complete` |
| `dragging` (slider thumbs) | `data-dragging` |
| `loading` (avatar images, progress) | `data-loading` |

```css
.menu-content[data-open] { animation: fade-in 150ms; }
```

```jsx
<Popover.Content className="opacity-0 data-open:opacity-100" />
```

A few more describe what the user is doing:

- Inside `Field.Root`, the field and its parts get `data-focused`, `data-touched`, `data-dirty`, `data-filled`, `data-valid` / `data-invalid`, `data-disabled` and `data-required`. Checkbox, Switch, Select and NumberField report these too.
- `ScrollArea.Root` and its scrollbars get `data-scrolling` and `data-hovering`; the root gets `data-has-overflow-x` / `data-has-overflow-y`.
- `Slider.Root` gets `data-dragging` during a drag, and `Avatar.Root` gets `data-loading` or `data-error` for its image.
- Positioned popups get `data-side` and `data-align` with the side and alignment they ended up on after collision handling.

## CSS variable fallbacks

Rad UI's tokenized styles expect the loaded theme CSS to provide the documented `--rad-ui-*` variables that those styles use.

Use CSS variable overrides as a layer on top of a complete theme:

```css
@import "@radui/ui/themes/default.css";

.billing-theme {
  --rad-ui-radius-md: 10px;
  --rad-ui-spacing-4: 1rem;
}
```

Do not treat `var(--token, fallback)` branches as a supported theming API unless the token guide documents that behavior for a specific variable. Fallback values may exist to keep internal migrations resilient, but consumers should not rely on missing variables resolving to Rad UI-chosen defaults.

See [Design Token Contract](/docs/guides/design-token-contract) for complete-theme and partial-override rules.

## What not to rely on

Avoid styling strategies that break when Rad UI refactors internals:

- deep descendant selectors against undocumented DOM nesting
- overriding private class names that are not part of your `classNamespace`
- `!important` rules that fight component state styles
- copying markup from Storybook and assuming incidental wrapper elements are stable
- replacing the default theme with a partial CSS variable map

If a style requirement needs a hook that does not exist, open an issue or PR to add a **documented** public attribute rather than targeting internals.

## Default theme vs bring-your-own

**Rad UI default theme**

```tsx
import '@radui/ui/themes/default.css'
import Theme from '@radui/ui/Theme'

<Theme classNamespace="rad-ui" appearance="dark">
  <App />
</Theme>
```

**Consumer design system**

- import Rad UI primitives per component
- map `data-*` attributes and slots to your tokens
- wrap primitives in your design-system components

Rad UI should not force a specific CSS framework. Tailwind, CSS Modules, SCSS, and CSS-in-JS are all valid as long as they target public hooks.

## Overriding the default theme with Tailwind

The default theme's CSS isn't in a cascade layer. Unlayered CSS beats every layered rule whatever its specificity, and Tailwind v4 puts its utilities in a layer, so a class like `text-2xl` on a `Heading` loses to the theme's own font size.

To let utilities win, import the theme into a layer of its own and place that layer between Tailwind's reset and its utilities:

```css
/* globals.css */
@layer theme, base, radui, components, utilities;
@import "@radui/ui/themes/default.css" layer(radui);
@import "tailwindcss";
```

The first line fixes the order of the layers. Rad UI's styles still beat Tailwind's reset (`base`), so buttons keep their look, and your utilities beat Rad UI's styles. The layer statement has to come first: if Tailwind declares its layers before `radui` exists, `radui` ends up last and wins again.

## Customization decision tree

1. Need one-off spacing or layout? → `className` on the relevant part.
2. Need state styling (open, checked, disabled)? → documented `data-*` attributes.
3. Need shared product theme? → `Theme` + optional theme CSS import.
4. Need a different visual system entirely? → headless usage + your tokens; do not import Rad UI theme CSS.

## Testing custom styles

When you ship custom CSS:

- verify focus rings remain visible
- test keyboard paths documented on each component page
- check contrast in both light and dark `Theme` appearances
- run SSR/hydration smoke tests if styles depend on client-only measurements

## Maintainer alignment

Library changes should preserve documented `data-*` attributes and public anatomy. Undocumented selectors may change in patch releases if they were never part of the supported contract.
