# CSS variables in practice

How the `--rad-ui-*` custom properties reach your CSS, how to scope them with nested `Theme`s, and what to do while a page is only partly on Rad UI. The token names themselves are in the [Design token contract](/docs/guides/design-token-contract).

## Where the variables come from

`@radui/ui/themes/default.css` defines every token on `:root` for the light appearance and overrides the colour families under `[data-rad-ui-theme="dark"]`. `Theme` puts that attribute, and `data-rad-ui-accent-color`, `data-rad-ui-radius` and `data-rad-ui-scaling`, on its container, so the values a component sees depend on the nearest `Theme` above it.

Without the stylesheet nothing defines the tokens, and the headless components don't need them.

## Nested themes

Each `Theme` is a scope. Put a dark `Theme` around a sidebar on a light page and every token inside resolves to the dark values, including `--rad-ui-color-accent-*` if the inner one names another accent:

```tsx
<Theme appearance="light" accentColor="blue">
  <main>…</main>
  <Theme appearance="dark" accentColor="violet">
    <aside>…</aside>
  </Theme>
</Theme>
```

To override a token for one scope, set it on that scope's container or match its attributes:

```css
[data-rad-ui-accent-color="violet"] {
  --rad-ui-color-accent-900: var(--brand-primary);
}
```

One caveat: the light values live on `:root`, so a light `Theme` nested inside a dark page inherits the dark colour tokens from the ancestor. Re-declare the light values on the inner container (this site does exactly that for its component previews) or avoid light-inside-dark nesting.

## Measured variables

Some components publish measurements as variables for animation: `Tabs.Indicator` sets `--active-tab-left` and `--active-tab-width`, `ScrollArea` sets `--scroll-area-overflow-y-start` and `-end`, nested dialogs set `--nested-dialogs`. They are part of the component's documented styling surface and exist with or without the theme. [Animation and transitions](/docs/guides/animation-and-transitions) shows each in use.

## Migrating a page gradually

While an app mixes legacy CSS with Rad UI, give your own rules a fallback so they render before the theme loads or on routes that never import it:

```css
.legacy-card {
  background: var(--rad-ui-surface-panel, #fff);
  border-radius: var(--rad-ui-radius-md, 8px);
}
```

Keep that to your own CSS. Rad UI's component styles expect the full theme; the fallbacks inside them are not a supported way to run with a partial token set.

## Checklist

- [ ] One `Theme` at the app root, more only where a section needs its own appearance or accent.
- [ ] Overrides sit on top of the imported theme, scoped to `:root` or a `Theme` container.
- [ ] Your CSS reads documented tokens and `data-*` attributes, not generated class internals.
- [ ] Light and dark checked for every nested scope.
