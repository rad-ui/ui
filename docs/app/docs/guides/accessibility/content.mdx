# Accessibility

Rad UI owns the parts of accessibility that are easy to get wrong and tedious to repeat: roles and states, keyboard handling, focus, dismissal, announcements. What it cannot own is yours: labels, contrast of your own colours, and the content inside.

This page says what the library does, what it leaves to you, and how to check both.

## What each component does

Every interactive component follows the matching [WAI-ARIA Authoring Practices](https://www.w3.org/WAI/ARIA/apg/patterns/) pattern, and its page documents the keyboard map and the ARIA references it implements. In short:

- **Roles and states** are set for you and kept in sync: `aria-expanded` on a trigger, `aria-checked` on a switch, `aria-selected` on a tab, `aria-invalid` on a field that failed validation. Native elements are used where one exists (a `button`, a `label`, a hidden `input` for form submission) and ARIA only where it is needed.
- **Keyboard**: composite widgets (menus, tabs, radio groups, toolbars, trees) are one tab stop; arrow keys move inside them, `Home` and `End` jump, typeahead finds items in lists. `Enter` and `Space` activate, `Escape` dismisses. Disabled items are skipped.
- **Focus**: dialogs trap focus while open and return it to the trigger on close; menus and popovers return focus too; nested dialogs close one at a time with `Escape`. Initial focus goes to the first sensible element, and every overlay has an `initialFocus` and `finalFocus` escape hatch.
- **Dismissal**: outside press and `Escape` close popups, and the event details say why, so you can veto a close ("discard changes?").
- **Announcements**: `Toast`, `Field.Error` and `LiveRegion` announce changes without moving focus. `Combobox` and `Select` report the active option through `aria-activedescendant`.
- **Pointer, touch and keyboard** get the same behaviour. `Slider`, `Splitter` and `Drawer` work with drag, arrow keys and touch.

## What stays with you

- **Names.** Give every control an accessible name: a visible `Field.Label`, a `label` with `htmlFor`, or `aria-label` for icon-only buttons. A `Dialog` needs a `Dialog.Title`; a `Tooltip` is not a name for its trigger.
- **Contrast.** Clarity's text and controls meet WCAG AA in both appearances, and this site's CI checks every page for it. The moment you use your own colours, that becomes your check: [WebAIM's contrast checker](https://webaim.org/resources/contrastchecker/) for pairs, axe in the browser for whole pages.
- **Focus visibility.** Clarity styles `:focus-visible` with a ring. If you restyle a component, keep a visible focus indicator with at least 3:1 contrast against its surroundings. Style `:focus-visible`, not `:focus`, so pointer clicks don't leave a ring behind.
- **More than colour.** Pair every colour cue with a second one, and use the `data-*` attributes that already exist:

  | State | Not enough | Enough |
  | --- | --- | --- |
  | Error | red border | red border + `aria-invalid` + a message in `Field.Error` |
  | Selected | hue change | icon or weight change keyed off `data-state="on"` |
  | Disabled | faded colour | `data-disabled` + `aria-disabled` + a non-interactive cursor |

- **Motion.** Clarity follows `prefers-reduced-motion`: motion tokens collapse to an instant duration, while a `Spinner` keeps turning because it carries meaning. If your CSS uses fixed durations, add the media query yourself ([Animation and transitions](/docs/guides/animation-and-transitions#respect-reduced-motion)).
- **Forced colours.** In Windows High Contrast the browser drops your colours. Clarity swaps its focus ring for a system-colour outline and keeps the fills that carry state (the Switch thumb, the Radio dot, the Slider range, the Tabs indicator, a pressed Toggle, the highlighted menu item). Check your own parts under `@media (forced-colors: active)` and use `Highlight` and `CanvasText`.

## Adjusting the defaults

Every part spreads its props onto the element it renders, so `aria-label`, `aria-describedby` and `aria-hidden` work directly. `asChild` moves a part's behaviour and ARIA onto your own element; use it to give a role to an element that should have it, not to borrow a part's look for an element with a different role ([Composition recipes](/docs/guides/composition-recipes#aschild-hands-over-semantics)). When a component's default behaviour is wrong for your case, prefer its documented props (`modal`, `initialFocus`, `disablePointerDismissal`) over removing attributes.

## Checking your work

1. Unplug the mouse. Reach every control with `Tab`, operate it with the keys on the component's page, and watch where focus lands after each overlay closes.
2. Run axe (the browser extension or `axe-core` in tests) on each screen in both appearances.
3. Walk the main flows with a screen reader once per release: VoiceOver on macOS and iOS, NVDA on Windows. [Screen reader testing](/docs/guides/screen-reader-testing) has a per-flow script.

Found a gap? Accessibility reports are triaged first: [open an issue](https://github.com/rad-ui/ui/issues) with the screen reader, browser and the announcement you got versus the one you expected.
